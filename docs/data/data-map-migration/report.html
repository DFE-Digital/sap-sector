Data map migration: errors fixed, platform improvements and follow-ups

The Excel data map (datamap.csv, 4,948 rows) has been replaced by code, and the pipeline now reloads only what changed. Along the way we found and fixed four KS4 mapping errors and several pipeline problems, including the daily establishment file not being reloaded. One change is visible on the website: around 3,650 schools now show a 2023 to 2024 grade 7+ figure for English language, English literature and Maths that was previously blank. Everything else the website shows is unchanged.

Platform improvements

Problems in how the pipeline loads and serves data, fixed as part of the migration.

ProblemWhy it matteredNowStatus
Daily establishment (GIAS) file was not reloaded. The rebuild lists named it edubasealldataYYYYmmDD, which never matches the dated daily file. School names, statuses, closures and links probably only refreshed when someone ran a full rebuild. Each day’s file loads automatically; the establishment view and the 6 school views that use it rebuild; yesterday’s tables are removed. Tested with a simulated next-day file. Fixed
Hand-kept rebuild lists decided which tables reload. Every new file needed a list edit; data map changes were never picked up; every run reloaded the listed tables whether or not they changed. The pipeline reloads a table only when its file changes and rebuilds a view only when its data or definition changes. No-change run: 2 s instead of 16 min. Fixed
Numbers stored as text. Taking the largest of several values compared them alphabetically (“9.66” beat “20.53”), which caused one of the KS4 errors. Every page had to convert text to numbers. Measures are numbers from the database through to the website. Checked cell by cell: no value the website shows changed. Fixed
Two copies of the same dataset loaded into one table where both a manual and a downloaded copy existed. Duplicated rows. One file per dataset (the manual copy wins). Fixed
Year labels hard-coded in 34 places on the website, separately from the data. A new data year could update the figures but not the labels. One shared setting per dataset drives both the data loaded and the labels shown. Improved
No checks on the data map. Mistakes were found in production, or not at all. Automatic checks run on every pull request and before each pipeline run. They found error 4 and would have caught all four KS4 errors. Improved
New data year was a large manual edit (about 1,300 spreadsheet rows for KS4). Slow, error-prone and hard to review. Change one year setting and the file names; a runbook and a dry run show what the checks report if files are missing or changed. Improved

Filters: three places, from general to specific

A DfE file usually has several rows per school, for example one per pupil group and year. Filters pick the one row a figure needs. All three kinds are combined, and each is written once instead of on hundreds of spreadsheet rows.

WhereApplies toExample
Source.Whereevery figure from that file.Where("time_period", "202425")
Source.Providesone pupil group in that file.Provides(Breakdowns.Eal, ("breakdown", "Known or believed to be other than English"))
Metric.Whereone measure.Where("subject", "Biology")

Design. Each part has one job: a definition says what to read, a rule checks one thing, a view line says where a view’s data comes from. New measures, rules and views are added alongside the existing ones rather than written into shared code, and the validator runs any class that follows the rule interface, so each rule can be tested on its own.

Proof. The restructure changed no output: the SQL generated before and after was compared in three pipeline modes (55 scripts each). Every table and view script is identical; the JSON export scripts differ only in spacing.

How these were found

The KS4 Performance part of datamap.csv (1,329 spreadsheet rows) was converted into a code-defined catalogue (Story 2). That step reproduces the spreadsheet exactly, including its mistakes, and a test proves the output is identical. Converting the rows into structured code made three inconsistencies stand out. Each was checked against the raw DfE source files before being fixed.

The fixes are in their own commits in pull request #372 (one for errors 1–3, one for error 4) so they can be reviewed, tested and, if needed, reverted separately from the migration. Error 4 was found by the automated data map validation added afterwards, which checks every field and filter value against the real source files.

Grade 7+ for 2023 to 2024 was blank for every school (English language, English literature, Maths)

What users saw
On the KS4 core subjects page with “Grade 7 and above” selected, the school’s 2023 to 2024 figure was missing for these three subjects. The other two years, and Biology, Chemistry, Physics and Combined Science, were fine.
Root cause
For the 2023 to 2024 school file only, these three subjects were mapped to filter on grades 7, 8 and 9. That file doesn’t contain single grades: it has grade bands (9 to 4, 9 to 5, 9 to 7). The filter matched nothing, so every school got a blank value.
Fix
Filter on the 9 to 7 band, the same as every other year and subject.

Local authority Progress 8 was one mislabelled, unreliable value

What users saw
Nothing today. No page shows LA Progress 8.
Root cause
Three spreadsheet rows (one per year) all used the same name, Prog8_Avg_LA_Previous2_Num, so only the first one was used. That row read 2024 to 2025 rather than 2022 to 2023, and filtered only on sex = Total. Every pupil group in the file (ethnicity, SEN, mobility and so on) has a sex = Total row, so the value was the largest across all of them, compared as text. For 2024 to 2025, Progress 8 isn’t published (z), so the result was z.
Fix
One properly named value per year (Prog8_Tot_LA_Current_Num, _Previous_Num, _Previous2_Num), each filtered to the all-pupils total row. This matches how school-level Progress 8 is named.

Data map clean-up

Removed with the spreadsheet; no change to any figure.

  • 1,994 rows marked ignore and 60 exact duplicate rows (pupil absence).
  • Establishment documentation rows that no code read and that had drifted from the real establishment view.
  • KS4 destinations year labels were a year ahead of the data (labels only; the website already showed the right years).
  • An unused LA Progress 8 field in the website’s data classes, replaced by the corrected per-year fields.
  • KS4 destinations, pupil absence, KS2, email, workforce and similar schools were migrated with no data errors found; each matches the spreadsheet exactly and passes the new checks.

How the fixes were verified

  1. Checked against source files. Each issue was confirmed in the raw DfE CSVs before changing anything, e.g. that the 2023 to 2024 file has a 9 to 7 band and no single grades, and that the engmath_95_* columns hold the grade 5+ figures.
  2. Automated tests. All 68 data map tests pass. The golden test compares the new catalogue with the old spreadsheet and fails unless the only differences are exactly these 26 columns, so any unplanned change is caught. The new validation checks every field and filter value against the source files and now runs in CI and before each pipeline run.
  3. Full pipeline run. The real pipeline was run end to end on PostgreSQL 16 (the production version) with the real source files, in a throwaway local database. It completed without errors and built all 23 views.
  4. Cell-by-cell comparison. The three KS4 views were built both ways (old spreadsheet and new catalogue) from the same raw data and compared value by value.
  5. All datasets, without the spreadsheet. After every dataset moved to code, all 22 views were rebuilt without datamap.csv and compared with the spreadsheet-built ones: identical, row for row. A full rebuild into a brand-new database ran all 52 pipeline scripts with no errors.
  6. Loading only what changed. Tested with no changes (nothing reloaded, 2 s), one changed file (only that table and its one view), a data map change (only the affected view) and a new day’s establishment file (3 tables, 9 views, old tables removed).
  7. In CI. The real pipeline ran from the branch against the test environment for review app 372: build, SQL generation and the database load all succeeded, and the review app backup was created.

What changes for users

  • KS4 core subjects page (/school/secondary/{urn}/ks4-core-subjects), with “Grade 7 and above” selected for English language, English literature or Maths: the school’s 2023 to 2024 figure now appears instead of being blank.
  • Similar schools average for those measures in 2023 to 2024 may change, because schools that were previously missing a value now count towards it.
  • Compare with a similar school (compare-ks4-core-subjects): both schools now show a 2023 to 2024 grade 7+ value for these subjects.
  • No change to grade 4+ and 5+, the other four subjects, KS4 headline measures, attendance, destinations, school details or primary pages.

Front-end testing is in progress on review app 372, using the example schools above.

Risks and considerations

  • New figures appearing. Users will see 2023 to 2024 grade 7+ values for the first time. They come straight from the published DfE file, but it may be worth a release note if these pages have been discussed with schools.
  • When it goes live. Nothing changes in any environment until the branch is merged and the data pipeline next runs.
  • Establishment data may start changing more often. If the daily file really hasn’t been reloaded in production, the first run after merge will bring school details up to date in one step. Worth checking before release (see follow-ups).
  • First run in each environment reloads everything once (about the time of a full rebuild), because there’s no record yet of what was loaded. After that, runs only reload what changed.
  • Website and pipeline must go out together. The website now expects numbers from the database; deploying one without the other would break the measure pages. They ship in the same pull request.
